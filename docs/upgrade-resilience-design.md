# 商家后台改版对抗设计（客户端稳定运行方案）

> 背景：美团/淘宝/京东/美团管家后台会持续改版（含灰度/A-B：同一时刻不同商家看到不同界面）。
> 结论先行：**「完美适配」不存在，改版必有窗口期**。工程目标是四个指标：
> ①你比客户先知道 ②故障被正确分类（瞬时 vs 结构性）③绝不产生错误数据 ④修复以热更新到达客户。

## 0. 改版影响的分层现实

| 层 | 稳定性 | 本产品依赖程度 |
|---|---|---|
| 导出文件格式（CSV 列名/列数） | 最稳（B 端报表少改） | **核心数据层**（营收/订单/店铺指标全在 CSV） |
| API 请求/响应结构 | 较稳 | 取文件直链、history 列表 |
| UI 流程（入口/步骤/按钮文案） | 中 | 登录、设参、点下载 |
| DOM 结构（选择器/类名） | 最脆（前端重构+灰度） | 日期控件、tab、全选、流量页读数 |

架构现状恰好正确：**数据正确性压在最稳层（CSV + 回读校验），DOM 只负责小接触面**。
后续原则：能走 API 不走 UI、能读文件不读 DOM、DOM 接触面只缩不涨。

## 1. 五层防线

### L1 选择器包热更新（核心机制）
- 所有页面锚点（JS 选择器、匹配文案、控件策略、文件名模式、列映射）从代码抽到
  `adapters/<platform>.json`：含 `pack_version` / `min_kernel` / `sha256`。
- 内核每次任务前从固定 URL 拉最新包（先用 GitHub raw，后可换 OSS），本地缓存，拉取失败用缓存。
- 改版时：改 JSON → 推送 → 客户下次运行即生效，**无需发版**。
- 支持变体分支：按页面指纹（某标记元素是否存在）在策略 A/B 间选择，应对灰度并存。

### L2 结构化失败分类 + 证据包
- 错误分类：
  - `E_TRANSIENT` 网络/慢加载 → 内核自动重试（已有 30s 看门狗/轮询语义）
  - `E_AUTH` 登录失效 → 走自动登录流程，验证码才升级人工
  - `E_STRUCTURAL` 元素找不到 / 回读不一致 / 列数异常 → **立即失败，不臆造**
- 已有验证门全部归入 E_STRUCTURAL 检测器：日期回读、62 格逐格校验、
  83/31 列数检查、拼好饭逐字节比对、交叉校验。
- E_STRUCTURAL 触发时收集诊断包：平台 + 步骤 + pack_version + kernel_version + 截图 +
  **脱敏 DOM 骨架**（只留 tag/class/文本长度，不留业务数值与凭据）。
- UI 一键「发送诊断」→ 飞书（复用现有飞书链路）。

### L3 自有账号金丝雀（dogfood）
- 用自家门店账号（梅溪湖）每天 cron 跑全平台 e2e，失败即飞书通知。
- 新 selector 包**先在自家账号跑通**再推送——灰度发布的"灰度"就是你自己。
- 回归测试无法放云端 CI（登录墙+风控），只能在自有环境日跑。

### L4 应急降级路径（客户侧不断数据）
- 已有 `skip_browser`：下载链路坏了但解析没坏时，客户手动从网页下载 CSV 放进目录 → 客户端解析填表。
- UI 做成显式「应急模式」入口 + 一页说明。
- 只有 CSV 格式本身变更（远比 DOM 改版罕见）才需要动映射包——映射也在 L1 包里。

### L5 LLM 的正确位置（维持既定红线）
- **客户机上：只做诊断建议，不执行修改、不自愈**。理由：改版自愈若选错锚点，
  会把错误数据写进经营报表——比"失败一天"严重得多。宁可失败。
- **开发机上：LLM/Jev 加速修复生产**。改版发生 → Jev 探新 DOM → 候选锚点 →
  人工审核 → 进 selector 包 → 自有账号 e2e → 推送。
  即：LLM 加速"修复流水线"，不进客户运行时。

## 2. 改版发生时的 playbook（时间线）

```
T0    客户任务失败 → 自动重试(瞬时) → 仍失败=结构性 → 收证据包+通知
T0+   你收到飞书 → 开发机复现 → Jev/LLM 探新 DOM → 出新包
T0++  自有账号 e2e 通过 → 推包 → 客户下次运行自动生效
```
目标：修复窗口 = 小时级；期间客户走应急模式或当天手工补。

## 3. 明确不做的事

- ❌ 客户机上 LLM 自动改选择器并重跑（风险 > 收益，见 L5）
- ❌ 追求覆盖一切 UI 变化的"完美适配"（灰度并存会让成本指数上涨；验证门+证据包更划算）
- ❌ 现阶段接官方开放平台 API（美团外卖开放平台需 ISV 资质/商家授权/审核，
  规模化后再评估——那是终极稳定路线）

## 4. 实施分期

- **Phase 1**：抽 meituan 选择器 → `adapters/meituan.json` + E_STRUCTURAL 错误分类 +
  诊断包（截图+脱敏 DOM）+ 飞书通知
- **Phase 2**：dogfood 日跑 cron + UI「应急模式」入口
- **Phase 3**：包签名/版本灰度/变体分支
- **Phase 4**（可选）：Jev 侦察工作流固化成 skill（京东 M5 首次使用）
